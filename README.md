# Продукты Даром

Бэкенд Telegram Mini App для каталога товаров со скидками и правил отслеживания. Сейчас работают вход через Telegram, пользовательские сессии и JWT. Каталог и отслеживания описаны в API, но пока возвращают `501 Not Implemented`: источник товаров и хранение правил не подключены.

## Стек

- Python 3.13+, FastAPI и Uvicorn
- SQLAlchemy Async, aiosqlite и SQLite
- Стандартные асинхронные миграции Alembic
- AuthX, Pydantic и Pydantic Settings
- APScheduler для очистки истёкших и отозванных сессий
- `uv` для зависимостей и запуска

Версии пакетов зафиксированы в `backend/uv.lock`.

## Запуск

Нужны Python 3.13+ и [uv](https://docs.astral.sh/uv/getting-started/installation/). Команды выполняются из корня проекта в PowerShell.

Установите зависимости и создайте локальный файл настроек:

```powershell
cd backend
uv sync
if (!(Test-Path .env)) { Copy-Item .env.example .env }
```

Укажите в `backend/.env` секрет подписи JWT и токен Telegram-бота. Для локального HTTP в примере окружения `JWT_COOKIE_SECURE=false`; на HTTPS установите `true`. Настройки загружаются простым `BaseSettings` из `.env` через Pydantic Settings. Секреты и локальные файлы базы не добавляются в Git.

Запустите приложение. Оно применит готовые миграции перед запуском сервера:

```powershell
uv run python -m app.main
```

Команда выше включает автоматическую перезагрузку при изменении кода. Для запуска без перезагрузки:

```powershell
uv run alembic upgrade head
uv run uvicorn app.main:app
```

При запуске через `python -m app.main` миграции выполняются через Python API Alembic до старта Uvicorn. На пустой базе применятся все готовые миграции, на существующей — только новые. При ошибке миграции сервер не запускается. Миграции выполняются один раз перед запуском наблюдателя и не повторяются при изменении кода. При прямом запуске Uvicorn миграции применяются отдельной командой, как в примере выше. `lifespan` настраивает логи, записывает сообщения о старте и остановке, выполняет очистку сессий при включённой настройке и затем запускает её по интервалу. При остановке планировщик завершается, а engine освобождает соединения с БД.

API доступно на `http://127.0.0.1:8000`, Swagger — на `http://127.0.0.1:8000/docs`, схема OpenAPI — на `http://127.0.0.1:8000/openapi.json`.

## API

Пути приложения начинаются с `/api`.

| Метод | Путь | Состояние |
| --- | --- | --- |
| `POST` | `/api/auth/telegram` | Вход по подписанным Telegram `initData` |
| `POST` | `/api/auth/refresh` | Ротация access/refresh пары |
| `GET` | `/api/auth/me` | Данные пользователя текущей сессии |
| `GET` | `/api/stores` | Контракт каталога, пока `501` |
| `GET` | `/api/categories` | Контракт каталога, пока `501` |
| `GET` | `/api/products` | Контракт каталога, пока `501` |
| `GET` | `/api/products/{product_id}` | Контракт каталога, пока `501` |
| `GET`, `POST` | `/api/tracking` | Контракты отслеживаний, пока `501` |
| `GET`, `PATCH`, `DELETE` | `/api/tracking/{tracking_id}` | Контракты отслеживаний, пока `501` |

Вход принимает исходную строку `initData` и обязательный UUID устройства в заголовке `X-Device-Id`. Сервер проверяет HMAC-подпись Telegram и срок её действия. Действующая сессия ищется по пользователю и устройству: повторный вход выпускает новую пару в той же записи. Если сессия отозвана или истекла, она заменяется новой с другим `session_id`. Refresh хранится в базе только как SHA-256-хеш; ротация атомарно заменяет хеш в той же сессии. Старый refresh отклоняется с `401`, отозванная сессия больше не авторизует запросы.

Лимит — 5 активных сессий на пользователя, настройка `MAX_ACTIVE_SESSIONS` в `.env`. При входе с нового устройства сверх лимита удаляются самые давно созданные активные сессии. Повторный вход на действующем устройстве не занимает новое место. Истёкшие и отозванные записи в лимит не входят. Refresh обновляет текущую запись и не создаёт новую сессию.

Клиент создаёт `device_id` один раз, сохраняет его и передаёт при каждом входе через Telegram. Для веба:

```javascript
let deviceId = localStorage.getItem('device_id')
if (!deviceId) {
  deviceId = crypto.randomUUID()
  localStorage.setItem('device_id', deviceId)
}
```

Значение `deviceId` передаётся заголовком `X-Device-Id` в `POST /api/auth/telegram`. Этот ID помогает найти сессию, проверку Telegram он не заменяет. `session_id` выдаёт сервер и записывает в JWT. Удаление локального хранилища означает новое устройство для приложения. В Swagger заголовок заполняется в поле `x-device-id` ручки входа.

При открытии Mini App клиент должен сначала запросить `/api/auth/me`, при 401 попробовать refresh и только при его неудаче заново войти через Telegram. Сессию определяют сохранённые JWT с `session_id`, привязка к User-Agent не требуется.

При входе и refresh сервер возвращает пару токенов в JSON и устанавливает JWT cookies штатными методами AuthX. Пара в JSON сохранена для будущего мобильного клиента. Обе cookies имеют `HttpOnly`, а параметры `Secure` и `SameSite` настраиваются. Cookie access имеет `Path=/api`, cookie refresh — `Path=/api/auth/refresh`.

CSRF cookies и проверки CSRF-заголовков в MVP отключены. В API нет маршрута выхода.

AuthX читает токены из источников, заданных в `JWT_TOKEN_LOCATION`: сначала JSON (`access_token` или `refresh_token`), затем cookies, затем заголовок `Authorization: Bearer ...`. Для веба достаточно cookies, для мобильного клиента доступны JSON и заголовок. Если токен найден, но не прошёл проверку, сервер возвращает `401`, а не пробует следующий источник.

Проверку access-токена выполняет штатная dependency AuthX. Общая функция `get_active_session` проверяет запись сессии и получает пользователя одним запросом к БД. Её используют `get_current_user` и обновление токенов. Каталог открыт без авторизации. Маршруты отслеживаний требуют авторизации и пока отвечают `501`.

## Фронтенд и прокси `/api`

Фронтенд вызывает API по относительным путям `/api/...`. Бэкенд не использует CORS middleware. Для работы браузера страница и API должны идти через один origin.

При локальной разработке Vite проксирует `/api` на Uvicorn. Добавьте правило в `vite.config.ts`, сохранив остальные настройки проекта:

```typescript
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    proxy: {
      '/api': 'http://127.0.0.1:8000'
    }
  }
})
```

Фронтенд отправляет, например, `fetch('/api/auth/me', { credentials: 'include' })`; указывать адрес бэкенда в URL запроса не нужно.

На сервере Nginx раздаёт собранный фронтенд из `dist` и передаёт `/api/...` на `127.0.0.1:8000`, сохраняя префикс `/api`. Добавьте настройки внутрь HTTPS-блока `server`, задав настоящий путь к `dist`, домен и сертификат. Uvicorn слушает локальный интерфейс. Для HTTPS задайте `JWT_COOKIE_SECURE=true`.

## Логи и фоновые задачи

Приложение использует стандартный `logging`: вывод в консоль и UTF-8 файл `backend/logs/app.log`. Файл ротируется при достижении 5 МБ, сохраняются три архива; уровень — `INFO`. Технические логи не хранятся в БД. Токены, Telegram `initData` и полные тела HTTP-запросов не записываются.

Сейчас APScheduler запускает только очистку сессий при старте и затем по интервалу из настроек. Бизнес-журналы, Redis, очередь и отдельный worker ещё не реализованы.

## Миграции и проверки

Конфигурация Alembic уже включена в проект. Для новой версии схемы измените модели, создайте миграцию и проверьте её перед применением:

```powershell
uv run alembic revision --autogenerate -m "add_products"
uv run alembic upgrade head
```

Запуск через `uv run python -m app.main` применяет готовые миграции автоматически. Отдельно их можно применить командой `uv run alembic upgrade head`. Справочные команды:

```powershell
uv run alembic current
uv run alembic history
uv run pytest
uv run ruff check .
```

Тесты используют отдельную временную базу. Для локального запуска не требуется изменять или передавать рабочую базу данных.
