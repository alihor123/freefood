# Продукты Даром

Бэкенд Telegram Mini App для просмотра продуктовых товаров со скидками и уведомлений по пользовательским правилам. Первый источник каталога — Магнит. Пользователь сможет найти товар и отслеживать его либо его категорию с заданным минимальным процентом скидки.

Сейчас работают вход через Telegram, JWT, сессии устройств и их очистка. Схема БД для каталога, правил и уведомлений создана миграциями. Продуктовые маршруты пока возвращают `501 Not Implemented`, а адаптер Магнита содержит только заглушки. Загрузка каталога и отправка уведомлений — следующий этап.

Подробное описание работающих функций и согласованного следующего этапа: [контекст бэкенда](backend/PROJECT_CONTEXT_BACKEND.md).

## Стек

- Python 3.13+, FastAPI и Uvicorn
- SQLAlchemy Async, SQLite и aiosqlite
- Alembic для изменения схемы БД
- AuthX для выпуска и проверки JWT
- Pydantic и Pydantic Settings для данных и конфигурации
- APScheduler для периодических задач, сейчас только очистки сессий
- uv для зависимостей и запуска

Версии зависимостей зафиксированы в `backend/uv.lock`. Redis сейчас не требуется и не подключён. Его возможная будущая роль — кэш часто запрашиваемых данных после измерения нагрузки. Для веб-клиента планируются React и TypeScript, для возможной самостоятельной мобилки — Kotlin и Jetpack Compose. Клиентов в этом репозитории пока нет.

## Запуск

Нужны Python 3.13+ и uv. Из корня репозитория перейдите в папку бэкенда и установите зависимости:

```shell
cd backend
uv sync
```

Создайте `.env` на основе [.env.example](backend/.env.example). Укажите `JWT_SECRET_KEY` и `TELEGRAM_BOT_TOKEN`. Для локального HTTP оставьте `JWT_COOKIE_SECURE=false`, для HTTPS установите `true`. Файл `.env`, рабочая база и логи исключены из Git.

Запустите сервер из `backend`:

```shell
uv run python -m app.main
```

При полном запуске сначала применяется `alembic upgrade head` через Python API, затем запускается Uvicorn с `reload=True`. Применённые миграции повторно не выполняются. При изменении кода сервер перезагружается без повторного запуска миграций. Если добавлена новая миграция, перезапустите всю команду или примените её отдельно.

Для запуска без автоматической перезагрузки:

```shell
uv run alembic upgrade head
uv run uvicorn app.main:app
```

Базовый адрес API — `http://127.0.0.1:8000/api`, Swagger — `http://127.0.0.1:8000/docs`, OpenAPI — `http://127.0.0.1:8000/openapi.json`.

Все дальнейшие команды uv в этом README выполняются из `backend`, где находится `pyproject.toml`.

## API

Общий префикс `/api` собирается в `app/main.py`.

| Метод | Путь | Состояние |
| --- | --- | --- |
| POST | `/api/auth/telegram` | Работает, вход и сессия устройства |
| POST | `/api/auth/refresh` | Работает, обновление пары токенов |
| GET | `/api/auth/me` | Работает, текущий пользователь |
| GET | `/api/stores` | Заглушка списка торговых сетей |
| GET | `/api/categories` | Заглушка списка категорий |
| GET | `/api/products` | Заглушка поиска, фильтров и пагинации |
| GET | `/api/products/{product_id}` | Заглушка карточки товара |
| GET, POST | `/api/tracking` | Заглушки списка и создания правил |
| GET, PATCH, DELETE | `/api/tracking/{tracking_id}` | Заглушки чтения, изменения и удаления правила |

Каталог публичный. Отслеживания требуют действующей авторизации. Вход принимает JSON с `init_data` и обязательный UUID в заголовке `X-Device-Id`. Создание отслеживания принимает ровно одну цель `product_id` или `category_id`, порог `min_discount_percent` и `is_active`. Магазин определяется по цели. Фильтры каталога и пагинация описаны в query DTO, параметры передаются в URL.

## Авторизация и сессии устройств

Клиент создаёт UUID устройства один раз, сохраняет его и передаёт в `X-Device-Id` при каждом входе через Telegram. Для веба:

```javascript
let deviceId = localStorage.getItem('device_id')
if (!deviceId) {
  deviceId = crypto.randomUUID()
  localStorage.setItem('device_id', deviceId)
}
```

После проверки подписи Telegram функция `login_with_telegram` находит или создаёт пользователя и вызывает `create_or_update_session`:

- Действующая сессия ищется по `user_id + device_id`. Повторный вход сохраняет её ID и заменяет пару токенов.
- Истёкшая или отозванная запись заменяется новой с другим `session_id`.
- На пользователя допускается пять активных сессий. При превышении лимита удаляются самые давно созданные активные записи.
- В БД хранится SHA-256-хеш refresh. Ротация атомарно заменяет его и `expires_at`, который означает срок действия текущего refresh.
- Старый refresh после ротации отклоняется. Старый access той же действующей сессии может работать до своего истечения.

`session_id` записан в JWT. После проверки JWT в AuthX общая функция `get_active_session` проверяет запись сессии и получает пользователя. Она используется и в `get_current_user`, и при refresh. Удалённая, отозванная или истёкшая сессия даёт `401`.

При открытии Mini App клиент запрашивает `/api/auth/me`, при `401` пытается обновить токены и только при неудаче refresh заново входит через Telegram. Устройство не определяется по User-Agent. Удаление сохранённого `device_id` будет считаться входом с нового устройства.

Пара токенов возвращается в JSON и устанавливается штатными методами AuthX в HttpOnly cookies. Access-cookie имеет `Path=/api`, refresh-cookie — `Path=/api/auth/refresh`. `Secure` и `SameSite` задаются настройками. JSON-пара сохранена для будущей мобилки.

Источники токенов заданы в конфиге AuthX: JSON, затем cookies, затем `Authorization: Bearer ...`. Если найденный токен недействителен, следующий источник не используется. CSRF-проверки и CSRF cookies в текущем MVP отключены. Маршрута выхода, ролей и permissions нет.

## Спроектированный следующий этап

Таблицы и DTO готовы. Бизнес-логика пока спроектирована на словах:

1. Планировщик раз в согласованный интервал запускает обновление каталога Магнита. Для этого не требуется очередь Redis.
2. Сервис получает данные, сравнивает их с предыдущим состоянием товаров и обновляет SQLite. Пользовательский API читает сохранённый каталог.
3. При изменении процента скидки создаются уведомления по подходящим активным правилам. Подходит и увеличение, и уменьшение, если новый процент не ниже порога.
4. Обновления товаров и события уведомлений сохраняются одной транзакцией для небольшой пачки. Отправка обрабатывает сохранённые события отдельно.

Пример для порога 30%: `35 → 50` уведомляет, `50 → 30` уведомляет, `30 → 30` не уведомляет, `30 → 0` только обновляет товар, `0 → 50` уведомляет снова. Не сравниваем с максимальной скидкой или всей историей сообщений.

В адаптере Магнита `request` будет получать исходные данные, а `parse_product` — преобразовывать одну карточку в общий `ProductData`. Сейчас обе функции выбрасывают `NotImplementedError`. Подробности будущих функций и нерешённые вопросы перечислены в [контексте](backend/PROJECT_CONTEXT_BACKEND.md).

## Фронтенд и прокси

Фронтенд обращается по относительным адресам `/api/...`. CORS middleware отсутствует: для браузера страница и API должны быть доступны через один origin.

В разработке задайте прокси в Vite:

```typescript
import { defineConfig } from 'vite'

export default defineConfig({
  server: {
    proxy: {
      '/api': 'http://127.0.0.1:8000'
    }
  }
})
```

На сервере Nginx раздаёт собранный фронтенд и передаёт `/api/...` на локальный Uvicorn, сохраняя префикс. Пример — [deploy/nginx.conf](deploy/nginx.conf). Домены, сертификаты и путь к фронтенду задаются для своего развёртывания. При HTTPS установите `JWT_COOKIE_SECURE=true`.

## БД, миграции и проверки

Рабочая база по умолчанию — `backend/freefood.db`. Схему меняют миграции Alembic. Текущая ревизия — `20261025_0004`. Продуктовые таблицы созданы, добавлена одна запись сети «Магнит» без вымышленных товаров и цен. Проверки отдельных значений находятся в DTO, связи и уникальность — в БД.

После изменения моделей создайте миграцию, проверьте её содержимое и примените:

```shell
uv run alembic revision --autogenerate -m "add_products"
uv run alembic upgrade head
```

Alembic хранит текущую ревизию в служебной таблице `alembic_version`. Он применяет только ещё не выполненные миграции. Создание новых файлов миграций автоматически при запуске приложения не происходит.

```shell
uv run alembic current
uv run alembic history
uv run pytest
uv run ruff check .
```

Тесты используют временные базы и собственные секреты. Они проверяют авторизацию, сессии, cookies, очистку, миграции, ограничения БД и контракт DTO.

## Логи и очистка

Стандартный logging пишет в консоль и UTF-8 файл `backend/logs/app.log`. При достижении 5 МБ файл ротируется, сохраняются три архива. Токены, исходные initData и полные тела запросов в эти логи не записываются.

Если очистка включена, при старте и затем каждые 24 часа выполняется один SQL DELETE истёкших и отозванных сессий. Интервал задаётся `SESSION_CLEANUP_INTERVAL_HOURS`. Дополнительного срока хранения завершённых сессий нет.
